# 2026-10-27

## 修复 Windows CI：cargo test 二进制 0xC0000139（STATUS_ENTRYPOINT_NOT_FOUND）

**根因链（PE 导入表二分截断实验实锤）**：
`ll-host`/`tauri-app` 依赖 tauri → muda/tauri-runtime-wry 静态导入 `comctl32!TaskDialogIndirect`（仅 comctl32 v6 有此导出）。
v6 需进程内嵌 Common-Controls 依赖清单经 SxS 激活。tauri-build 经 embed_resource 的 `link-arg-bins` 只给 bin 嵌清单，
测试二进制无清单 → 绑定 System32 comctl32 v5 → 进程启动即崩。Linux 无此分裂故正常。

**修复**：
- 新增 `src-tauri/crates/ll-host/build.rs` + 改 `src-tauri/build.rs`：Windows 目标用 `embed_resource::compile_for_everything`
  （`cargo:rustc-link-arg`）把 Common-Controls v6 清单链进所有目标。
- ⚠️ 坑：`compile_for_tests`（`link-arg-tests`）**不覆盖 lib 单测**，包内无 tests/ 目标时 Cargo 直接报错。
- app 侧同时 `WindowsAttributes::new_without_app_manifest()` 关掉 tauri 的 bins-only 清单，防双 RT_MANIFEST（MSVC 重复资源）。
- 两 crate 加 build-dependencies `embed-resource = "3"`。
- CI rust-cache 第一行 `. -> target` 改为 `. -> src-tauri/target`（target-dir 被 .cargo/config.toml 钉走，原配置缓存空转）。

**顺手修的本地既有问题**：MinGW（windows-gnu）下 tauri-app 的 cdylib 无 #[no_mangle] 导出 → ld 回退
auto-export-all（157129 符号 > 65535 导出序号上限）→ "export ordinal too large"，本地完全无法构建 app。
修法：`src-tauri/build.rs` 在 gnu 目标发 `cargo:rustc-link-arg-cdylib=-Wl,--exclude-all-symbols`（桌面 cdylib 无消费方）。
对照实验确认该问题与清单修复无关（原版 build.rs 同样失败）。

**验证**：本地 `cargo test --workspace` 全绿（57 测试，0 失败）；`cargo build -p tauri-app --bins` 成功；
bin 与测试 exe 中 Common-Controls 清单恰好 1 份。CI 为 MSVC：webview2-com-sys 静态链接 WebView2LoaderStatic，无 DLL 拷贝需求。
