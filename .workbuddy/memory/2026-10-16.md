## 第二轮审计（换框架：任务成本 × 可发现性）
- 新框架结论：操作路径已经很短（3 步内完成绝大多数任务），**瓶颈全在"进入之前"——想不到、不知道语法**。继续压缩按键无收益。
- 三个新发现：
  1. **`/help` 渲染失效（P0）**：`builtinHelpPlugin.ts` 是全仓唯一把 description 拼成多行（join('\n')，含 examples/argsHint/热键）的地方，而 `launcher.css` 的 `.item-description` 是 `white-space:nowrap + ellipsis` 单行截断 → 所有示例与用法在面板里看不见。**发现机制本身不可见**（自指 bug）。
  2. **契约填充率低**（实测 34 插件）：argsHint 8 个（24%）、examples 9 个（26%）、hotkeys 2 个。契约设计正确但七成能力对新用户等于不存在。
  3. **`PanelItem.category` 是死字段**：`command.ts:68` 定义了 category，ResultPanel 从不渲染，全仓无任何插件设置它。分组表达力预留但从未兑现。
- 其他：托盘菜单仅 2 项（显示/退出），无设置/热键速查入口；`fuzzyScore` 候选指令匹配只用 trigger/name/id，裸文本"url 编码"这类**意图词召不回 /hash**；冷启动空态无任何"试试这些"。
- 建议顺序：修 /help（改 CSS 或加 detail 字段）→ 插件质量门（plugin:test 里断言 argsHint/examples 非空）→ 面板承载升级（多行 detail + category 分组启用）→ 意图词纳入候选匹配 → 空状态能力橱窗。

## 第三轮审计（换框架：Nielsen 十项启发式）+ 三视角汇总
- 评分 28/50（中上）。低分五项：状态可见性 2、识别优于回忆 2、错误恢复 2、帮助文档 2、灵活性与效率 3。
- 本轮新发现（均有代码证据）：
  1. **破坏性操作零护栏**：`plugins/bookmark/bookmark.py:114` `del` 分支直接删并回 `已删除`，无确认无撤销；todo 完成态切换同样不可撤销。
  2. **反馈通道四路并存**：壳层 Toast（22 个插件）+ 系统通知（pick/shot）+ 桌面弹窗（todo ReminderToast）+ 桌面挂件（pomo）——同一类"操作成功"在不同插件里表现完全不同，无统一契约。
  3. **帮助断层**：argsHint 只在候选面板（未匹配到插件时）显示；**一旦输入 `/hash ` 匹配成功，用法提示就消失了**——最需要提示的时刻恰恰没有提示。无 `?` 类上下文帮助入口。
  4. **无收藏/固定机制**：34 个能力完全扁平（pomo 的 pin 是贴壁纸，非收藏）。高频 3-4 个与偶用 30 个无区分度。
  5. **模式不可见**：输入被路由到数学/Action/Query/搜索，唯一指示是 18px 的 prefixIcon 变化，用户无法预知这次回车会发生什么。
  6. **错误文案透传**：`❌ ${res.message}` / `执行异常: ${err.message}` 直接暴露技术异常串，无"下一步怎么办"的指引。
- **三视角收敛的四条根因**（写进结论，是后续改进的总纲）：
  ① 反馈层无人负责（四通道并存、无统一契约）；② 面板表达力封顶（各限一行 + category 未启用）；③ 能力进入路径缺失（help 失效 + 填充不足 + 无收藏）；④ 破坏性操作无护栏（删除/状态切换不可撤销）。
- 三视角互补关系：① 四态审计→反馈态缺口；② 任务成本×可发现性→瓶颈在进入之前；③ Nielsen→信任与发现欠账。三者独立得出、相互印证，说明这套问题是结构性的而非偶发。
