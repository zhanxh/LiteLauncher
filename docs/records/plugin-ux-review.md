# LiteLauncher 插件交互体验评审与市场对标

> **历史快照（2026-10-13）**：本文记录当时的问题与对标，不随实现实时更新。
> 当前能力以 `CHANGELOG.md` 与代码为准；优化执行记录见
> [optimization-plan.md](../design/optimization-plan.md)。

> 评审对象：`docs/records/plugin-roadmap.md` 所列 A/B/C/D 组功能
> 评审方式：路线图与实际代码逐条核对（`src/App.tsx`、`plugins/*/fe`、`plugins/*/*.py`）+ 主流同类软件公开资料对标
> 结论口径：问题均标注代码位置或来源；未实现能力标注为"缺口"，不臆测已实现

## 0. 结论先行

1. **功能层面"广度"已经够了**——31 个外部插件 + 4 个编译期插件，覆盖纯计算、个人工具、网络、桌面四类，路线图 §0 列的三项需求（哈希/截图/取色）都已闭环。
2. **但"桌面级"三件套只落地了最窄的一种交互形态**：`/shot` 是"全屏存盘 + 路径进剪贴板"，而市场主流是"框选 + 图片本体进剪贴板"。**这一个差距就足以让用户装 Snipaste 而不是 LiteLauncher**——因为截图后粘出一串路径，无法直接使用。
3. **优先级建议（性价比排序）**：
   - **P0 截图图片直进剪贴板**（改一处宿主能力，成本最低、感知收益最大）
   - **P0 区域框选截图**（补 `ViewSpec` 的 fullscreen/transparent + 拖拽层）
   - **P1 剪贴板历史 `/clip`**（Windows 效率"必装三件套"之一，目前完全缺失，且需先做隐私设计）
   - **P1 取色器补滚轮缩放 + 光标处直接取色**
   - **P2 文件搜索**——**建议先做技术选型决策，不要直接开工**（详见 §4.4，路线图当前的依赖判断偏乐观）

## 2. 交互问题清单（按严重度分级）

### 🔴 阻塞级：直接决定产品能否被替代品取代

#### P0-1 截图复制的是"路径字符串"而非图片本体

- **证据**：`plugins/shot/fe/src/index.ts:122` `await ctx.clipboard.write(shot.path)`；热键路径 `:280` 同理。
- **市场对照**：Snipaste（F1 截图→图片已在剪贴板）、ShareX（默认"复制到剪贴板 + 保存到文件"）、Win+Shift+S（复制图片）、PixPin（复制图片）。**没有一款主流工具把路径给你**。
- **为什么是阻塞级**：截图的核心动作是"看到 → 立刻粘到聊天窗口/文档/工单"。当前流程需要：唤起启动器 → 输 `/shot` → 选屏 → 找到刚才那张图 → 再插入。**功能可用性 ≠ 交互可用性**。
- **建议**：`svc.screen.capture` 增加 `toClipboard: true`（宿主侧把 PNG 字节经 arboard 写为图片格式，**不经 base64**，插件零改动）。成本约 20 行宿主代码。

#### P0-2 缺少区域框选

- **证据**：roadmap §11.6 自述未做，根因是 `ViewSpec` 无 `fullscreen`/`transparent`。
- **市场对照**：矩形/圆形/自由形状/窗口/全屏是标配（ShareX 15+ 种模式）。**全屏截图在日常占比极低**，"截某个区域"才是主路径。
- **建议**：`ViewSpec` 补两个声明位 → 宿主开一个全屏透明置顶层 → 拖拽选区 → 复用已有 `capture_region`（坐标换算逻辑已在 `hit_rect` 中验证过）。这是 P0-2 唯一阻塞项。

### 🟡 严重：影响留存但不致命

#### P1-1 网络类插件需两次回车

- **证据**：roadmap §10.2 范式——`query()` 只渲染一条「查询」项，用户回车才真正发请求，再回车才复制。
- **对照**：Alfred / Raycast / uTools 均为**输入即出结果**（靠全局索引与预取缓存）。
- **客观约束**：壳层对插件 `query()` **逐键调用且无防抖**（`App.tsx:218` 直接调 `result.plugin.query`，而 `searchRegistry` 那条路径才有 50ms 防抖 `App.tsx:270`）。所以"输入即请求"会打爆网络。
- **建议**：**不要在插件层硬改**，应给壳层加一个可选的 `queryDebounceMs` 插件声明字段（默认 0 保持兼容），网络插件声明 300ms。这样范式可以简化成"输入即出结果"，且不破坏既有插件。

#### P1-2 取色器缺"滚轮缩放 + 光标处直接取色"

- **证据**：`panel.tsx` 固定 320×350 于右下角（`pick/manifest.json` `position: bottom-right`），按钮在面板内（`:195-204`），无 `wheel` / `keydown` 监听。
- **对照**（PowerToys Color Picker 官方文档）：放大镜**浮层跟随光标**、**滚轮缩放**、**中键取色即退出**、**Esc 取消不复制**、编辑器支持 HSV 微调 + 相似色建议 + 颜色名称（"Light Green"）+ 自定义格式模板。
- **判断**：当前"面板常驻 + 移入冻结"路线在**反复对比多色**场景其实优于 PowerToys 的"取一次关一次"，不必全盘照抄。但**必须补**：滚轮缩放、Esc 取消、光标处单击即取（不必移到面板）。这三条是用户肌肉记忆的默认动作，缺失会让人觉得"别扭"。

#### P1-3 剪贴板历史缺失（能力空白，非交互问题）

- 宿主**无后台监听**，路线图 §2 标为"需 clipboard:read + 后台监听 + db"。
- **这是"必装三件套"之一**：Everything（搜索）/ 截图 / 剪贴板历史。缺它，LiteLauncher 在"效率工具"心智里就少了一条腿。

#### P1-4 `/help` 信息量不足

- **证据**：`builtinHelpPlugin.ts` 全文 44 行，条目只有 `title` + `description`，**无一条语法示例**。
- **对照**：uTools 每个插件都有独立说明页与示例。
- **建议**：`/shot -d3`、`/hash md5 <文本>`、`/fx 100 USD CNY` 这类**真实示例**是插件作者已经写在 manifest description 里的，结构化后直接暴露即可，成本极低、收益立竿见影（新用户不知道 `-d3` 怎么用）。

### 🟢 一般：打磨项

#### G-1 壳层剪贴板实现不统一（疑似真 bug）

- **证据**：`App.tsx:307` 数学计算结果走 `navigator.clipboard.writeText`，而通用路径 `applyCopy`（`:353`）走宿主 `invoke('clipboard_write')`。
- **风险**：`navigator.clipboard` 要求页面聚焦，数学结果复制后**不隐藏窗口**（`:305-312` 无 `hideWindow`），所以当前恰好不出问题；但两条路径并存意味着**后续任何一处加 `hideWindow` 就会踩竞态**。roadmap §9.2 已明确记录过这个坑。建议统一到 `applyCopy`。

#### G-2 面板高度魔法数字导致"还有更多"不可见

- **证据**：`App.tsx` 中 `updateWindowHeight(420)`（:186、:222）、`124`（:167）、`260`（:246）、`70`（:166）写死。`/hash` 12 条时每条 56px 需要 672px，被裁到 420px。
- **表现**：`.panel-container` 有 `overflow-y: auto`（`launcher.css:195`）能滚，但滚动条 6px 极细（`:201`），用户**不知道自己下面还有内容**。
- **建议**：面板底部加渐隐遮罩 + "还有 N 项"提示，是低成本的"可滚动"信号。

#### G-3 `/shot` 面板混入了不可执行的"说明条目"

- **证据**：`shot/fe/src/index.ts:206-223` 的 `action: 'none'` 两项（截图存放位置、全局热键说明），`onSelect` 走到 `:255 return {}` —— **按回车无任何反馈**。
- **问题**：箭头键会导航到它们，制造"按了没反应"的死条目。
- **建议**：改为置顶胶囊（壳层已有 `PreviewCapsule` 机制）承载说明，或 `action:'none'` 时给 `{toast: '该项是说明'}` 明确反馈。

#### G-4 候选指令补全不带参数提示

- **证据**：`App.tsx:364` `setInputValue(item.metadata.trigger + ' ')`。
- **对照**：uTools 补全会带参数占位提示。
- **建议**：manifest 增加 `argsHint`（如 `/shot` → `[屏序号] [-d秒]`），补全时带出。这是插件作者可自助填写的字段。

#### G-5 截图落盘无上限、无清理

- **证据**：`svc.screen.capture` 落盘到插件目录，无数量/容量上限、无过期策略。
- **对照**：ShareX 支持自动命名规则 + 自动保存路径 + 保留策略。
- **风险**：长期使用会缓慢撑大磁盘，且用户不知道东西存哪（`/shot` 面板里那条说明恰好暴露了这个无知）。

## 4. 市场实现方式对标

> 以下均为各产品官方文档 / 项目主页公开信息，用于对照**通用交互范式**，不复制其专有实现。

### 4.1 截图类

| 产品 | 核心交互 | 关键能力 | 对 LiteLauncher 的启示 |
|---|---|---|---|
| **Snipaste** | `F1` 截图 → `F3` 贴图 | **贴图钉屏**（缩放/旋转/透明度/置顶/分组）、截图历史回放、截图时按 `C` 直接复制色值 | "贴图"是它区别于所有竞品的招牌。用户对照设计稿/表格数据时刚需 |
| **ShareX** | `PrtScn` 区域截图 | 15+ 模式（矩形/圆形/自由形状/**滚动截图**/网页截图/自动识别窗口）、标注（箭头/文字/马赛克/模糊/高亮/**步骤编号**）、录屏、OCR、**截后自动化工作流** | "截完自动做事"（存+复制+命名）是高阶设计；步骤编号是教程场景刚需 |
| **PixPin** | 区域/窗口/全屏 | **长截图**（自动滚动拼接，对代码编辑器优化）、**离线+云端 OCR**、录屏 GIF | 长截图与 OCR 是它对 ShareX 的差异化 |
| **FastStone Capture** | — | 极致轻量、所见即所得的标注 | 轻量本身是卖点 |

**共性结论**：截图三步是 **触发 → 框选 → 图片已在剪贴板**。LiteLauncher 停在第 1 步和"存盘"，且第 3 步给错了内容（路径）。

### 4.2 取色器类

| 产品 | 核心交互 | 关键能力 |
|---|---|---|
| **PowerToys Color Picker** | `Win+Shift+C` → **放大镜浮层跟随光标** → 中键取色即退出 / Esc 取消 | **滚轮缩放**（冻结图像后取"非悬停态"颜色——一个很聪明的技巧）、多显示器/多 DPI 感知、**感知屏幕边界并留在安全区**、HSV 微调、相似色建议、**颜色名称**（Light Green）、**可自定义格式模板**、历史 20 条 |
| **Snipaste** | 截图中移动光标按 `C` 复制 HEX | 取色与截图**合并为一个动作** |

**架构参考**（PowerToys 公开的模块文档）：C++ DLL 宿主 + **独立 UI 进程** `PowerToys.ColorPickerUI.exe`，通过共享事件通信；历史落本地 JSON（ARGB 字符串按行存储）。**取色器用独立进程的理由是"崩溃隔离 + 不阻塞宿主"**——LiteLauncher 的取色台是独立 Tauri 窗口，方向一致。

**共性结论**：**光标处直接取**是默认肌肉记忆，"移到面板点按钮"是反模式。

### 4.3 剪贴板历史类

| 产品 | 实现方式 | 隐私设计 |
|---|---|---|
| **Ditto**（开源，20 年） | 本地 **SQLite**，无限历史，**正则搜索**，支持文本/图片/HTML/RTF/自定义格式 | **local-first，无账号无云无遥测**；可**按应用排除**（密码管理器）；可断开监听；置顶分组；加密网络同步；便携模式 |
| **Windows Win+V** | 内置，**上限 25 条 / 单条 4MB**，未置顶项被新项挤出 | 可选云同步 |
| **uTools** | 剪贴板增强插件 | 图片缩略图、收藏常用片段 |

**关键洞察（Ditto 官方与安全分析的共同结论）**：这类工具的价值与风险同源——**救回一小时前命令的工具，同样会保存密码、API token、验证码**。Ditto 之所以被推荐，正因为它 local-first；而建议同时是：限制条数与有效期、公共机禁用、处理凭据时先断开监听。

> **对 LiteLauncher 的前置要求**：`/clip` 必须**先做隐私设计再写功能**——默认排除密码管理器类应用、条数上限 + 过期时间、显式开关、明确告知数据落本地。这不是可选项。

### 4.4 文件搜索类 —— 技术路线需要重新决策

**Everything 的实现方式**（公开资料）：
- 启动时读取 **NTFS MFT**（主文件表）建内存索引 —— **不遍历目录、不发起额外磁盘读**
- 通过 **USN Journal**（变更日志）增量更新，更新周期通常 **1–5 秒**
- 仅索引**文件名与路径**，**不索引文件内容**
- 代价：**需管理员权限**读 USN 日志、**仅支持 NTFS**、多用户环境下不安全（结果不按当前用户权限过滤）

**对照路线图 §2 的判断**：`/find` 被列为"需要 `fs` 作用域 + `index`"。**这个判断偏乐观**——`fs:dir:<scope>` 声明式作用域做的是**目录遍历**，本质上是"更慢的 Windows 搜索"，**没有存在价值**（Everything 的价值 100% 来自 MFT 索引）。

**三条路，必须选一条**：

| 方案 | 能力 | 代价 | 建议 |
|---|---|---|---|
| A. MFT + USN 索引 | 可对标 Everything | 需 Windows 服务 + 提权；与"纯用户态插件"模型冲突；仅 NTFS | ⭐ 唯一有竞争力的方案，但**架构级改动** |
| B. 作用域目录遍历 | 只搜用户指定目录 | 性能与 Windows 搜索同级 | ❌ 无差异化，不建议 |
| C. 明确降级 | 诚实标注"仅搜索已标记目录" | 能力弱 | 兜底方案 |

**建议**：先出技术选型决策（是否接受 Windows 服务 + 提权），再排期。**不要按当前 roadmap 直接开工**。

### 4.5 启动器交互范式（跨品类共识）

| 产品 | 共识做法 |
|---|---|
| **uTools** | `Alt+Space` 全局框；**自动识别剪贴板内容**（复制 JSON/时间戳/链接后自动匹配对应插件）；模糊拼音首字母；**超级面板**（选中文字/文件，中键呼出，自动适配：文字→翻译/OCR/二维码，图片→压缩/图床/去背景） |
| **Quicker** | **上下文面板**：面板下半部分**随前台软件自动切换**（Excel 显示 Excel 专属操作，Chrome 显示浏览器操作）；上半部分固定；**多种触发**（中键/侧键/长按/滑动/画圈/文本指令）；**轮盘菜单** |
| **Alfred / Raycast** | 文件搜索强项；剪贴板历史；扩展生态 |

**三条可直接借鉴的低成本交互**：
1. **剪贴板内容自动路由**——复制一段 JSON 后唤起，自动进 `/json`。（`clipboard.read` 已就绪，只差壳层一个"唤起时读剪贴板"的入口）
2. **选中即唤起（超级面板）**——选中文字调出适配工具集，比"先复制再唤起再粘贴"少 3 步。
3. **悬停预览**——面板项 hover 时右侧显示大图/完整内容。`PreviewCapsule` 机制已存在，可扩展。

## 5. 三条"看似小、实则影响大"的改动

### 5.1 截图图片直进剪贴板
宿主 `svc.screen.capture` 加 `toClipboard` 参数，走 arboard 写图片。**约 20 行，插件零改动**，直接消灭 P0-1。

### 5.2 `ViewSpec` 补 `fullscreen` + `transparent`
这是**解锁区域框选截图与全屏遮罩取色的唯一开关**。同时要注意 roadmap §11.3 ⑥ 记录的坑：新增视图窗口**必须在 `src-tauri/capabilities/default.json` 的 `windows` 白名单登记**（标签 = `<pluginId>-<viewId>`），否则该窗口零权限、变死窗。

### 5.3 壳层给插件加可选 `queryDebounceMs`
让网络插件从"两次回车"回归"输入即出结果"，同时不破坏逐键调用假设。
